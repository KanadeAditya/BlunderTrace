# Pre-build research: can retrieval explain chess mistakes?

This folder holds the research done **before** building BlunderTrace: the test data, scripts, corpus
and results that decided how the product's retrieval works. None of it is product code.

**Main finding:** embeddings understand language, not chess positions. Retrieval works when the
search is about the **chess idea** ("what is a pin, how do I avoid it"), and fails when it's about
the **board**. So the product needs a separate way to understand positions and find mistakes. The
corpus only supplies the theory that explains them.

---

## 1. What we set out to build

BlunderTrace is an AI chess coach. It looks at a player's recent games, finds the mistakes they
**keep repeating**, and explains them in plain English with cited chess theory. The plan was a RAG
(retrieval-augmented generation) system that recognises chess patterns:

1. Take a mistake from the player's game.
2. Search a corpus of chess teaching text for passages about similar situations.
3. Have an LLM write an explanation grounded in those passages.

The open question: **can a text-embedding search connect a chess position to the right teaching
text?**

## 2. The embedding problem

Embedding models turn **language** into numbers. Chess positions are normally stored as PGN (the
move list) or FEN (a one-line board code), for example
`r1bq1rk1/pp2bppp/2n1pn2/3p4/3P4/2NB1N2/PP3PPP/R1BQ1RK1 w - - 0 10`. Embedding those strings is
meaningless: two FEN strings that look alike can be completely different positions, and the
reverse. PGN and FEN can't be embedded usefully, so they were never tried.

The idea we did test was a workaround: **translate each position into plain English first**, with
a deterministic function, `describe(board)`, and embed that:

> *Mistake by White: allowed a fork. Middlegame. White is ahead by 2 points of material. White has
> doubled e-pawns. Black has an isolated b-pawn and a backward f-pawn. The c- and d-files are open.
> White's king is stuck in the centre and can no longer castle. Black to move.*

If this worked, a player's position and a teaching position would sit close together in embedding
space, and search would connect them. **This report tests that idea, and it doesn't work.**

## 3. How we tested it

### Test queries: 45 real mistakes, not written by hand
To stop the test from being tuned to the corpus (test leakage), the queries were **generated by
code from real data and frozen in git before any corpus existed.**

- **Source:** the Lichess open puzzle database. Every puzzle comes from a real game in which a
  player made a mistake. It records the position, the move actually played, and **theme labels
  assigned by Lichess** (fork, pin, hanging piece…).
- **Sample:** 45 puzzles, 5 from each of 9 themes (fork, pin, skewer, discovered attack, hanging
  piece, back-rank mate, trapped piece, exposed king, advanced pawn). Club-level ratings
  1000–1800, fixed random seed 42.
- **Query text:** `describe()` of the position right after the mistake, in two styles:
  - **full:** the mistake plus the whole board description (above)
  - **short:** just the mistake and phase, e.g. *"Mistake by White: allowed a fork. Endgame."*
- Files: `queries.md` (readable), `queries.jsonl` (used by the scripts), `sample_puzzles.py`.

### Corpus: 2,425 rows from five sources, no AI used
| Source | Rows | What it gives |
|---|---|---|
| Lichess studies (6 instructional studies) | 321 | Positions with human comments |
| Wikipedia (36 concept articles + Glossary of chess) | 1,155 | Concept explanations (fork, pin, isolated pawn…) |
| Wikibooks "Chess" (10 chapters) | 136 | Tutorial-style tactics, strategy and endgame text |
| Project Gutenberg: Capablanca's *Chess Fundamentals*, E. Lasker's *Chess Strategy* | 766 | Classic theory; prose only, paragraphs heavy in move notation dropped |
| Lichess puzzle-theme glossary | 47 | One-line definitions of each tactical theme |

All rows share one shape: `id, source, title, section, url, text, fen (studies only), meta`.
Readable copies are in `corpus/readable/`.

### Six corpus versions × two query styles
| Version | What gets embedded |
|---|---|
| A_raw | Study comments as written |
| B_template | Study comments with study, chapter, opening, phase and move in front |
| B2_describe | `describe()` of the commented position + the comment (the original design) |
| C_concepts | Wikipedia, Wikibooks, Gutenberg, theme glossary |
| D_mix | B2 + C (everything) |
| D_mix_no_themes | D without the theme glossary (checks whether its overlap with the test labels inflates scores) |

### Search and scoring
- **Embeddings:** OpenAI `text-embedding-3-small`. 3,139 texts, 225,880 tokens, **$0.0045 in
  total**. That was the only API use; no chat models were called.
- **Search:** exact cosine similarity with numpy (the same ranking pgvector gives without an
  index), top 5 per query.
- **Self-check:** 20 corpus rows searched with their own embedding must come back as #1.
  **Passed 20/20**, so the search code works.
- **Automatic score (hit@5):** the share of queries where at least one of the top 5 results
  mentions the puzzle's theme, using a fixed keyword list per theme.
- **Blind human check:** a shuffled sheet with version names hidden was prepared. It was skipped
  for this run because the failure was obvious from the automatic score and the raw results.

## 4. Results

**Automatic score:** share of the 45 queries with at least one relevant result in the top 5.

| Version | Full query | Short query |
|---|---|---|
| A_raw | 2% | 27% |
| B_template | 9% | 11% |
| B2_describe | 13% | 18% |
| C_concepts | 24% | 27% |
| D_mix | 13% | **31%** |
| D_mix_no_themes | 13% | 31% |

By theme (D_mix, full query), forks, skewers, discovered attacks, trapped pieces, exposed king
and advanced pawns all scored **0 of 5**. Every query and its top 5 per version are in
`results/top5.md`; the tables are in `results/summary.md`.

### Why it failed
1. **Board descriptions match other board descriptions, not lessons.** With full queries, **225
   of 225** top-5 slots in D_mix went to study rows whose `describe()` text *sounded* similar
   ("Endgame. White is ahead by 2 points… isolated a-pawn…", similarity 0.83). None were about the
   actual mistake. The few words that mattered ("allowed a fork") were drowned out by about 60 words
   of board description.
2. **Framing words dominate short queries.** *"Mistake by White: allowed a fork"* retrieved old
   game notes such as *"This is a mistake. The right move was R - Q 1…"*. The search matched
   "mistake" and "White", not "fork".
3. **Much of the corpus is the wrong kind of text** for explaining mistakes. Study comments and
   annotated games narrate individual moves ("Developing move to control d4"); they don't explain
   concepts.

Removing the theme glossary changed nothing (31% → 31%), so its overlap with the test labels
didn't inflate the score.

### Follow-up check: is the right content there at all?
To separate "bad corpus" from "bad question", each theme's glossary definition (e.g. *"Pin: A
tactic involving pins, where a piece is unable to move without revealing an attack on a higher
value piece."*) was used as a concept-only query. It searched the corpus with the glossary
removed, reusing existing embeddings at no cost.

| Theme | Relevant in top 5 | Found in |
|---|---|---|
| pin | 5/5 | Wikipedia Pin, Glossary, Wikibooks Tactics |
| skewer | 5/5 | Wikipedia Skewer, Chess tactic, Wikibooks |
| back-rank mate | 5/5 | Wikibooks Checkmates, Wikipedia Checkmate pattern |
| discovered attack | 4/5 | Wikipedia Discovered attack, Chess tactic |
| advanced pawn | 4/5 | Glossary, Wikibooks Strategy, Promotion article |
| hanging piece | 2/5 | Glossary "hanging" ranked #1 |
| trapped piece | 1/5 | Glossary "trapped piece" ranked #1 |
| exposed king | 1/5 | Glossary "exposed king", "mating attack" |

**All 8 themes found relevant text**, 27 of 40 results on-topic (fork was missing; see
limitations). **The corpus contains the right theory. The question was the problem.**

## 5. Conclusions

1. **Embeddings can't understand chess positions,** whether as PGN/FEN or as plain-English board
   descriptions. They match wording, not chess meaning.
2. **Retrieval works for chess *ideas*.** Asking about the concept finds the right explanations,
   mostly from Wikipedia, Wikibooks and the glossary.
3. **More data isn't the fix.** The corpus (2,425 rows) already contains the theory. A few themes
   (trapped piece, exposed king, hanging piece) have thin coverage and may need a few targeted
   additions, not bulk fetching.
4. **Board facts belong in the LLM prompt and in metadata filters, not in the embedded text.**

## 6. What we'll build instead

To make this work, we need something that **understands the board** and tells us what went wrong.
That's a chess engine's job, and **Stockfish** fits:

1. **Find the mistakes.** Stockfish analyses each of the player's games and flags the moves that
   lost the most evaluation. For each one it gives the better move and the **opponent's winning
   reply**: the line that punishes the mistake.
2. **Name the mistakes.** Code applies chess heuristics (python-chess) to the engine's line to
   label each mistake with a known blunder type. For example, if the punishing move attacks two
   pieces at once, it's "allowed a fork"; if the punished piece had no defenders, it's "left a
   piece hanging".
3. **Find the patterns.** Count mistake types across all games to get the player's **top recurring
   issues**: "you allow forks (11×)", "you leave pieces hanging (7×)".
4. **Retrieve the theory.** For each top issue, search the stored corpus with a concept question,
   e.g. *"how to avoid allowing a fork"*, and take the best passages with their sources.
5. **Explain it.** The LLM receives the engine's facts (the mistake, the better move, the winning
   reply) plus the retrieved theory, and writes a plain-English explanation with citations. It
   never calculates moves; an output validator checks that every move it mentions comes from the
   engine's line.
6. **Ask box.** Free-text follow-up questions use retrieval directly. This is where RAG is needed
   most, because a fixed lookup table can't answer open questions.

The product direction is similar to recurring-mistake tools such as
[AuditChess](https://www.producthunt.com/products/audit-chess/makers), which analyses many games
to surface a player's repeated mistakes. BlunderTrace adds **retrieved, cited theory** explaining
each top issue and how to fix it.

Before the build, retrieval will be re-tested on a **fresh, unseen set of puzzles** (new seed,
frozen first), with concept-style queries and the blind human check as the main measure.

## 7. Limitations of this study

- **The keyword score is crude.** "Hanging pawns" (a pawn-structure term) counted as a hit for
  *hanging piece*, and "mating attack" counted as a miss for *exposed king*. Human judgement is the
  better measure.
- **The follow-up check used Lichess's own polished definitions as queries,** which is a best case.
  Real queries will be short concept questions written once per mistake type.
- **Corpus bug:** the theme glossary has no *Fork* row, because Lichess names that description
  `forkOpposingPiecesDescription`. To be fixed before the re-test.
- **The 45 queries have now been seen.** Further tuning must be checked on a new, unseen set.
- **Lichess study content belongs to its authors,** and Wikipedia/Wikibooks text is CC BY-SA.
  Check terms and attribution before any public launch.

## 8. Reproducing

All commands run from inside `pre_build_research/` (it is its own uv project). Embeddings are cached in `cache/` (gitignored), so
re-runs cost nothing; on a fresh clone, `build --yes` re-embeds for about $0.005.

```bash
uv run python sample_puzzles.py           # regenerate the 45 queries (same seed)
uv run python fetch_studies.py <studyId>  # download a Lichess study
uv run python build_corpus.py             # build corpus/*.jsonl from all sources
uv run python make_readable.py            # readable copies in corpus/readable/
uv run python retrieval_test.py build     # dry run: shows tokens and cost, no API call
uv run python retrieval_test.py build --yes  # embed (embeddings model only)
uv run python retrieval_test.py query     # self-check, scores, results/top5.md
uv run pytest                             # 20 tests, no API calls
```
